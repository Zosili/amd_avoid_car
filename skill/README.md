# skill/ —— 可复用能力包

> 对应《选题指南》3.2.5.3 与 3.2.2.5。每个模块都是**能独立跑起来的脚本**，
> 与本题目的具体实现解耦：换一台机器人、换一块板卡，只要接口契约一致就能复用。

## 0. 为什么这些能复用

本作品的四类操作在开发中反复出现，且**每次都要重新踩一遍同样的坑**：

| 模块 | 反复踩的坑 | 沉淀成什么 |
|---|---|---|
| `hwh_probe` | 插上了、没反应，不报错——因为 PL 里根本没有那个 IP | 一个只读的“到底有没有接上”的确认 |
| `radar_probe` | 串口逐字节读，吞吐跟不上数据率，FIFO 溢出丢字节却不报错 | 能分清“没接上”“接上了但丢字节”“数据本身有问题”的探针 |
| `bench_infer` | 把首次编译/预热算进延迟，报出来的数是假的 | 分离预热与稳态、报分位数而非均值 |
| `latency_stats` | 跨日志拼时间轴，算出几百万毫秒的间隔 | 按文件独立统计，报 P50/P95/P99/max 与未命中率 |
| `check_timing` | 只看 `All constraints met`，不看具体 WNS 和违例端点 | 把报告解析成结构化判据，可串进构建脚本 |

**共同点**：它们判定的都是“这条路通不通、稳不稳”，而不是“这个功能有没有”。
所以换场景、换硬件之后，判据依然成立。

## 1. 五步定位阶梯（最重要的一条方法）

外设“不工作”有五种完全不同的原因，混在一起会浪费一整晚。按这个顺序走，
每一步都有一个可判定的结论，**失败了就知道停在哪一层**：

| 步 | 查什么 | 判据 | 失败说明 |
|---|---|---|---|
| ① | `.hwh` 里有这个 IP 吗 | `hwh_probe` 列出目标 IP 与基址 | bitstream 里根本没接这个外设 |
| ② | PL 配置成功了吗 | `cat /sys/class/fpga_manager/fpga0/state` → `operating` | 位流没加载，引脚是“哑”的 |
| ③ | IP 有时钟吗 | 写一个字节后 `tx_empty=1` | FCLK 没使能 / aclk 没接 |
| ④ | 引脚与波特率对吗 | **短接 TX-RX 做回环**，收发一致 | 接线错 / 波特率偏差 / 电平不匹配 |
| ⑤ | 传感器本身有问题吗 | 字节率与帧率达到标称值 | 只剩传感器侧的原因 |

**第 ④ 步是整个阶梯的支点**。短接 TX-RX 后能收到自己发的字节，说明
“IP + 时钟 + 引脚 + 波特率”整条路都对，问题必然在传感器侧；
收不到，则说明问题在自己这边。没有这一步，你会在接线和代码之间反复怀疑。

> 本项目实测：第 ① 步就能定性 —— 当时板子上跑的 bitstream 里根本没有 `axi_uartlite`。
> 表现是“插上了、没反应、不报错”，因为那两根引脚在 PL 里没被任何逻辑占用，
> 等于悬空导线。补上 IP 重新出位流后，第 ② 步立刻通过。

### 触碰 MMIO 前必须先确认的三件事

1. 位流确实加载成功（`state = operating`）
2. 该 IP 的 aclk 有频率（FCLK 已使能）
3. 只访问 `.hwh` 里明确给了基址的 IP

**为什么这条是硬规矩**：对未时钟化的 AXI slave 做一次寄存器读，会让 AXI 总线挂死，
板子当场失去响应（ping/SSH 全无，ARP 也消失），**只能断电重启**。本项目真实发生过一次。
所以 `hwh_probe` 被刻意设计成**只解析、不碰 /dev/mem**，与读写测试分成两个命令。

## 2. hwh_probe —— 只读解析 .hwh

**适用范围**
任何从 Vivado 导出的 `.hwh`（Zynq-7000 / UltraScale+ 通用）。不依赖 PYNQ、不碰硬件。

**使用方法**
```bash
python hwh_probe.py motor.hwh
python hwh_probe.py motor.hwh --expect uartlite --baud 230400
```

输出每个 IP 的名称、类型、基址、关键参数；带 `--expect/--baud` 时给出判据。

**失效条件**
- `.hwh` 没导全（不是合法 XML）→ 直接报“不是合法 XML”
- 只读 hwh，**不能**用它证明硬件可用；硬件可用性要靠后面的回环与数据率
- 部分版本 hwh 把基址放在 `MEMRANGE` 而非 `PARAMETER`，脚本两种都试

**已验证的复用结果**
- 本作品 `motor.hwh`：`axi_gpio_0 @0x41200000`（32 位）、
  `axi_uartlite_0 @0x42C00000`（baud 230400）、`processing_system7_0`
- 换另一块 7020 板卡的 hwh，无需改动

## 3. radar_probe —— 串口传感器链路探针

**适用范围**
任何通过串口输出定长帧的测距传感器。默认按 COIN-D6 解析（`AA 55` 帧头、85 字节帧），
换协议只改 `parse_frame()` 一处。

**使用方法**
```bash
# PC 侧（原厂 CH340 转接板，最省事的一条路）
python radar_probe.py --port COM5 --baud 230400 --secs 10 --nominal-fps 170

# 板载 AXI UART Lite —— 注意：PYNQ 默认不加载 uartlite 驱动，
# 板上没有 /dev/ttyUL0，pyserial 那条路走不通，必须用 MMIO 后端
python radar_probe.py --mmio 0x42C00000 --secs 12 --nominal-fps 170
```

两个后端（`--port` / `--mmio`）**判据完全相同，只是"字节从哪来"不同**——
这是本包"接口契约不变、只换取数方式"的典型例子。

四项判据：

| 判据 | 合格线 | 不合格说明什么 |
|---|---|---|
| 帧率 | ≥ 标称的 90% | 吞吐不够，或解析卡住 |
| 坏帧率 | ≤ 1% | 校验失败多 → 丢字节 / 波特率偏 |
| 有效点率 | ≥ 80% | 回波弱 → 镜头脏 / 被测面吸收 / 超量程 |
| 帧长 | **主导**帧长等于标称值（85 B） | 主导长度错 → 协议版本不对 |
| （提示）其它包长 | 只列出不判失败 | COIN-D6 会发多种包（n=1/23/24，长度 13/79/82），校验和合法 |

**失效条件**
- 波特率高于 921600 时 Python 逐字节读可能跟不上，应改用 DMA 或内核驱动
- **AXI UART Lite 的 RX FIFO 只有 16 字节**：230400 下约 0.7 ms 余量，必须紧循环轮询。
  实测字节率明显低于 14.4 KB/s、或 `overrun` 计数增长，说明轮询太慢（PS 被抢占了）
- 串口被占用时直接报错，不会静默返回 0 帧

**已验证的复用结果**
- **PC 侧 CH340**：169.5 帧/s、坏帧 0、有效点率 92.9%（桌面）／98.1%（手举空中）
- **板载 AXI UART Lite（MMIO 后端，2026-11-04 实测）**：12 s / 2012 帧、
  **167.7 帧/s**（标称 170 的 98.6%）、坏帧率 1.04%、主导帧长 85 B —— 吞吐与解析都对。
  完整输出见 `metrics/evidence/radar_probe_board.md`
- 同一次板载测量里**有效点率只有 43.5%**，判据如实报 FAIL：雷达静置桌面、扫描面朝空旷处，
  大量光束打不到东西，自然没有回波。**没有为了好看去放宽阈值或挪动设备**——
  判定工具如果会为结果让步，它就没有价值
- 顺带量出一个差异：同一链路，PS 侧 `ps_radar_fusion.py` 自报坏帧约 **3.5%**，
  探针测得 **1.04%**，说明"逐字节 + 业务逻辑"的读法确实比纯轮询丢得多

## 4. 接线核对卡（学自一次“插上没反应”）

| 检查项 | 正确做法 | 错了会怎样 |
|---|---|---|
| 交叉 | 板子 TX(U9) → 雷达 RXD；板子 RX(U8) ← 雷达 TXD | 接成直通 → 一个字节都收不到 |
| 共地 | 雷达 GND 必须接板子 GND | 不共地 → 乱码或 0 字节 |
| 供电 | 雷达 5V **单独供电**，不要从 J4 取电 | J4 的 3.3V IO 只有几 mA，带不动 |
| 电平 | 雷达若 5V TTL，进 3.3V PL 引脚前要分压 | 长期可能打坏 IO |
| 短接自检 | 先短接 U9-U8 跑回环 | 能区分“IP 问题”和“雷达问题” |

**四条接法里只有两条通**（本项目实测）：
① USB 原厂转接板 → PC：**现在就能用**；
② TTL 直连 PL：需要 bitstream 里有 `axi_uartlite`；
③ TTL 直连 PS 串口：设备树 `serial@e0001000` 是 disabled，运行期 overlay 改不动端口号
（`uart_add_one_port() failed; err=-22`），重编 DTB 才通；
④ USB 插板子的 USB_HOST：chipidea 控制器从未 probe，dmesg 零记录。

## 5. bench_infer —— 目标检测推理基准

**适用范围**
任何 onnxruntime 可加载的模型。后端可切：CPU、DirectML、ROCm、VitisAI。

**使用方法**
```bash
python bench_infer.py --model best.onnx --backend dml --input 1x3x640x640 --n 100
python bench_infer.py --model best.onnx --backend cpu --n 30 --compare dml
```

**关键约定**
- **预热与稳态分离**：前 N 帧单独计时并丢弃，NPU/GPU 首次会编译并写缓存
- **分位数而非均值**：延迟分布长尾，均值掩盖卡顿
- **预处理/推理/后处理分开报**：否则不知道瓶颈在哪

**失效条件**
- 模型输入尺寸与 `--input` 不符时直接报错
- 后端不可用时列出可用 provider，不静默回退
- 只测推理本身，不测收图与解码；端到端要另算

**已验证的复用结果**
- 本包 `host/model/best.onnx`（19 类，1×3×640×640，随机输入、**纯前向**，预热 10 帧后取 60 帧）：
  DirectML（Radeon 780M）P50 **3.6 ms** / P99 3.8 ms，CPU P50 **47.0 ms**，**约 13 倍**
  （`ort 1.23.0.dev`，2026-11-04 01:05 实测，`--backend dml --compare cpu`）
- 同脚本在只有 CPU 的机器上跑，输出结构与判据不变

> **口径别混**：上面是"只做前向"的数字，不含收图、letterbox、后处理与发帧。
> 检测主程序里端到端约 **16 ms/帧**、整环 5~6 fps（见 `metrics/metrics.csv`），
> 两者是对同一模型的不同切面，不能拿来互相印证，也不能混着写进报告。

## 6. latency_stats —— 控制环延迟统计

**适用范围**
任何以 JSONL 逐行记录时间戳的实时控制环。字段契约：`{"t": <unix_ms>, ...}`。

**使用方法**
```bash
python latency_stats.py logs/*.jsonl --period 100
```

**关键约定**
- **按文件独立统计，绝不跨文件拼时间轴**。不同 run 的 `t` 来自不同会话甚至不同机器时钟
- **未命中率比均值重要**：均值 100 ms 但每 10 帧卡一次 500 ms 的环，均值看不出来

**失效条件**
- 缺 `t` 字段或非毫秒时间戳 → 报错并指出第一行
- P50 明显偏离 `--period` 时给出提示（环可能没按预期跑）

**已验证的复用结果**
- **本作品融合环（2026-11-04 01:54，341 帧 / 78.1 s，原始记录随包提供）**：
  帧间隔 P50 **257 ms** / P95 309 / P99 316 / max 417，抖动 P99 116 ms，平均 4.37 fps
- 同一份数据顺带量出：推理耗时 P50 **16.5 ms**，只占帧间隔的 **6%** ——
  也就是说这个环 94% 的时间在**等图**，瓶颈在图传不在 AI。
  这条结论直接否掉了"推理太慢所以帧率低"的常见误判
- 抓到过两次真实异常：交互式绘图阻塞主循环（P99 4323.9 ms）、周期配成 3.3 Hz
  而未命中率 93% —— 说明判据真的在起作用

**一个重要口径**：未命中率假设环有**固定标称周期**，只适用于定时环。
本项目的环是**帧驱动**的（有图才跑），用 `--period 200` 会得到 50% "未命中"——
那不是故障，是按定义一半样本在 200 ms 以上。对帧驱动的环应当用 `--period 0`
（只报分位数），或按实测中位值再判定。详见 `metrics/evidence/latency_run.md`。

## 7. check_timing —— Vivado 报告判据化

**适用范围**
任何 Vivado 工程。读 `timing_summary_routed.rpt` 与 `utilization_placed.rpt`。

**使用方法**
```bash
python check_timing.py --reports ./fpga/report --min-wns 0.5
```

**失效条件**
- 报告名不同 → 用 `--timing` / `--util` 显式指定
- 实现未完成或报告为空 → 报“报告缺失”，不返回 PASS
- 只解析 7 系列/Zynq 常见字段，UltraScale 的额外列被忽略

**已验证的复用结果**
- 本作品（位流 md5 `1fc79ab4…`，2026-11-03 22:27）：WNS **+1.356 ns**、WHS **+0.010 ns**、0 违例；
  LUT **4.38%**、FF **2.57%**、BRAM 0.36%、DSP 0%、IOB 36.80%
- 原始报告已随包提供在 `fpga/report/`（`timing_summary_routed.rpt`、`utilization_placed.rpt`），
  上面那条命令可直接在仓库根目录复跑
- 迁到另一块 7020 同规模工程，脚本无需改动

## 8. 迁移到新场景时的检查顺序

换了机器人或换了板卡，按这个顺序过一遍：

1. `hwh_probe` —— 目标外设在不在这份 bitstream 里（只读，零风险）
2. `fpga_manager state` —— PL 配置成功没有
3. **短接回环** —— IP/时钟/引脚/波特率这一层对不对
4. `radar_probe` —— 传感器侧通不通、丢不丢字节
5. `bench_infer` —— 推理后端能不能用、延迟够不够
6. `latency_stats` —— 控制环周期稳不稳
7. `check_timing` —— 改了 RTL 之后时序还收不收敛

**前四步是“链路可信”的前提**，没走完不要开始调功能。
任何一步摸棱两可，都说明那条链路不可信。

## 11. 一条命令自检

判断"这套工具在当前仓库能不能用"，不用逐个敲：

```bash
python skill/selftest.py               # 离线项：hwh 结构 + 时序/资源
python skill/selftest.py --with-infer  # 额外跑推理基准（需要 onnxruntime 与模型）
```

- 默认两项都**只读**、不碰硬件；
- 任一 FAIL 退出码为 1，可直接串进 CI；
- 缺文件时打印 `[SKIP]` 并算作未通过，不会假装成功。

实测输出：

```
[PASS] hwh_probe（这份 bitstream 里有没有 axi_uartlite）
[PASS] check_timing（时序收敛 + 资源占用）
----------------------------------------------------
全部通过。注意：这只说明『链路判定工具本身可用』，
不代表板子在跑、也不代表车能避障——那要上电实测。
```

> 最后那句不是客套：工具通过 ≠ 系统可用。真正的链路验证仍要走第 1 节的五步阶梯。
