# skill 功能介绍

> 本文件说明作品提交仓库中 `skill/` 目录**是什么、解决什么问题、怎么用**。
> 对应《2026 FPGA 创新设计赛道选题指南（AMD）》3.2.5.3（Skill 与工作流）与 3.2.2.5（可复用能力封装）。

---

## 一、一句话定位

**它是一套“链路能不能信”的判定工具，不是功能代码。**

竞赛要求提交物的可复用性，判分点不是“代码有多少行”，而是：
**一支没参与过开发的队伍拿到这个目录，能不能直接用到自己的题目上。**

所以 `skill/` 里没有避障逻辑、没有状态机、没有阈值表——那些和具体题目绑定，换场景就要重写。
里面装的是**判定方法**：怎么确认一条链路真的通了、而不是“看起来通了”。

---

## 二、它要解决的问题

### 2.1 症状相似，原因完全不同

嵌入式联调里最耗时的不是写代码，是**从一个现象倒推到原因**。
本作品开发过程中遇到过五类“不工作”，外观几乎一样，根因却分属五个层次：

| 现象 | 真实原因 | 第一反应会怀疑的 | 实际排查耗时 |
|---|---|---|---|
| 传感器插上了，一帧都没有，且不报错 | PL 里根本没接 `axi_uartlite`，引脚是悬空导线 | 接线 / 驱动代码 | 约 3 小时 |
| 有数据，但坏帧率 30% | 串口逐字节读只有 13 KB/s，追不上 23 KB/s 数据率，FIFO 静默溢出 | 传感器坏了 | 约 2 小时 |
| 推理延迟报到 200 ms | 把首次编译与预热算进了统计 | 模型太大，要换小模型 | 约 1 小时 |
| 日志里出现 4323 ms 的周期 | 跨两次 run 拼了时间轴，两个机器时钟混在一起 | 主循环卡死 | 约 2 小时 |
| Vivado 报“约束全部满足”，实际有违例端点 | 只看了汇总那一行，没看违例端点数 | 时序没问题，继续往下走 | 约 1 小时（且差点漏到提交） |

这五件事的共同点是：**“看起来对”和“确实对”之间的差距，恰好是工具该填补的位置。**

### 2.2 迁移到新场景时的问题放大

本项目从 PC 侧摄像头链路迁到板载雷达链路时，同一个传感器出现了两种接法
（USB 转接板 / TTL 直连 PL 引脚）。前者能跑，后者一个字节都收不到——但**两次的现象描述完全一样**：
“雷达没数据”。

如果没有分层判据，只能靠猜。有了五步阶梯，第二次故障在 15 分钟内定位到
“bitstream 里缺 IP”，而不是在接线和代码之间来回改。

## 三、五个工具，各解决一层

| 工具 | 回答的问题 | 关键设计 | 依赖 |
|---|---|---|---|
| `hwh_probe.py` | 这份 bitstream 里到底有没有那个外设？ | **只读不写**，零风险 | 标准库 |
| `radar_probe.py` | 传感链路通不通、丢不丢字节？ | 四项判据而非“有没有数据” | pyserial |
| `bench_infer.py` | 推理多久、首次与稳态差多少？ | 预热与稳态分离 | onnxruntime |
| `latency_stats.py` | 控制环稳不稳？ | 按文件独立统计 | 标准库 |
| `check_timing.py` | 时序还收不收敛、资源够不够？ | 报告判据化，可串进构建 | 标准库 |

### 3.1 hwh_probe —— 先确认“有没有”，再谈“好不好”

解析 Vivado 导出的 `.hwh`，列出每个 IP 的名称、类型、基址、关键参数，
并按需检查波特率与时钟频率是否匹配。

**为什么它必须只读**：
对没有时钟的 AXI slave 做一次寄存器读，会让 AXI 总线挂死，板子当场失去响应
（ping、SSH、ARP 全部消失），**只能断电重启**。本项目真实发生过一次。
所以“确认有没有”和“试着读写”被刻意拆成两个命令，前者永远安全。

### 3.2 radar_probe —— 区分“没接上”“接上了但丢字节”“数据有问题”

四项判据：

| 判据 | 合格线 | 不合格说明什么 |
|---|---|---|
| 帧率 | ≥ 标称的 90% | 吞吐不够，或解析卡住 |
| 坏帧率 | ≤ 1% | 校验失败多 → 丢字节 / 波特率偏 |
| 有效点率 | ≥ 80% | 回波弱 → 镜头脏 / 被测面吸收 / 超量程 |
| 帧长一致性 | 全部等于标称值 | 协议版本不对 |

只有第一项的话，会漏掉“能读到但吞吐跟不上”这一类**静默失败**——
FIFO 持续溢出、字节在丢，但程序不报错，只是数据看起来稀稀拉拉。

### 3.3 bench_infer —— 报稳态，不报“第一次”

三条约定：

1. **预热与稳态分离**：前 N 帧单独计时并丢弃。NPU/GPU 首次会编译并写缓存，
   混进去会虚高数倍——本项目的模型首次比稳态慢一个数量级。
2. **报分位数而非均值**：延迟长尾，均值掩盖卡顿。
3. **预处理 / 推理 / 后处理分开报**：否则不知道瓶颈在哪一环。

### 3.4 latency_stats —— 均值会骗人

两条硬规矩：

1. **按文件独立统计，绝不跨文件拼时间轴**。不同 run 的时间戳来自不同会话甚至不同机器，
   拼起来会算出几百万毫秒的“间隔”。
2. **报未命中率，不只报均值**。均值 100 ms、但每 10 帧卡一次 500 ms 的环，
   均值显示正常，产线会出事。

### 3.5 check_timing —— 把“人眼扫报告”变成“脚本给结论”

读 `timing_summary_routed.rpt` 与 `utilization_placed.rpt`，
输出 WNS/TNS/违例端点数、WHS，以及 LUT/FF/BRAM/DSP/IOB 占用，
最后给一行 PASS/FAIL，可直接串进构建流程。

存在的理由：人眼容易只看 `All user specified timing constraints are met` 那一行，
不看具体余量和违例端点数。脚本不会。

## 四、核心方法：五步定位阶梯

这是整个 skill 里最值钱的一条，写在 `README.md` 第 1 节。

外设“不工作”有五种完全不同的原因，混在一起会浪费一整晚。
按这个顺序走，**每一步都给出一个可判定的结论，失败了就知道停在哪一层**：

| 步 | 查什么 | 判据 | 失败说明 |
|---|---|---|---|
| ① | `.hwh` 里有这个 IP 吗 | `hwh_probe` 列出目标 IP 与基址 | bitstream 里根本没接这个外设 |
| ② | PL 配置成功了吗 | `fpga_manager/fpga0/state` → `operating` | 位流没加载，引脚是“哑”的 |
| ③ | IP 有时钟吗 | 写一个字节后 `tx_empty=1` | FCLK 没使能 / aclk 没接 |
| ④ | 引脚与波特率对吗 | **短接 TX-RX 做回环**，收发一致 | 接线错 / 波特率偏差 / 电平不匹配 |
| ⑤ | 传感器本身有问题吗 | 字节率与帧率达到标称值 | 只剩传感器侧的原因 |

### 第 ④ 步是支点

短接 TX-RX 后能收到自己发的字节，说明「IP + 时钟 + 引脚 + 波特率」**整条路都对**，
问题必然在传感器侧；收不到，问题就在自己这边。

没有这一步，排查会退化成在“是不是线接错了”和“是不是代码写错了”之间反复怀疑，
而这两个方向的验证成本都很高。

## 五、为什么算“可复用”

按 3.2.5.3 的四要素逐条对照：

| 要求 | 本包的做法 |
|---|---|
| **适用范围** | 每个工具的 README 段落开头都写明，且限定在“接口契约一致”的前提下 |
| **使用方法** | 每项给出可直接复制的命令行，参数化（端口、波特率、模型、周期、报告路径） |
| **失效条件** | 每项列出 3 条左右，写明“什么情况下这个工具会给出错误结论” |
| **已验证的复用结果** | 每项附本项目的实测数字，以及“换设备后是否仍然一致” |

**解耦的证据**：

- `hwh_probe` 不依赖 PYNQ，任何 Vivado 导出的 `.hwh` 都能解析
- `radar_probe` 的协议解析集中在 `parse_frame()` 一个函数，换传感器只改这一处
- `bench_infer` 的后端是参数，换机器换后端不用改代码
- `latency_stats` 与 `check_timing` 只用标准库，且字段契约写得极简（一个 `t` 字段 / 两个报告文件）

## 六、怎么用

```bash
# 0) 装依赖（只用标准库的三个脚本不需要这步）
pip install -r skill/requirements.txt

# 1) 拿到新板子/新工程，先只读确认（零风险）
python skill/hwh_probe.py motor.hwh --expect uartlite --baud 230400

# 2) 确认 PL 已配置
cat /sys/class/fpga_manager/fpga0/state      # 必须是 operating

# 3) 短接 TX-RX，做回环  —— 这一步是整个阶梯的支点
python skill/radar_probe.py --port COM5 --baud 230400 --secs 10 --nominal-fps 170

# 4) 推理基准（换机器后最先变化的就是这个）
python skill/bench_infer.py --model best.onnx --backend dml --n 100

# 5) 控制环
python skill/latency_stats.py logs/*.jsonl --period 100

# 6) 时序与资源
python skill/check_timing.py --reports ./fpga/report --min-wns 0.5
```

**顺序不能颠倒。** 前四步没走完，不要开始调功能；任何一步摸棱两可，
都说明那条链路不可信，后面所有数据都要打问号。

## 七、边界：它不解决什么

- **不替代功能测试**。它回答“这条链路通不通、稳不稳”，不回答“车会不会避障”。
- **不包含业务逻辑**。帧怎么解析、阈值怎么定、状态机怎么跳，与题目绑定，换场景要重写。
  skill 复用的是判定方法，不是判定内容。
- **两个脚本未当场验证**：`radar_probe` 需要串口设备，`bench_infer` 需要模型文件，
  本次提交前未在干净环境跑通完整流程，仅给出用法与判据。其余三个已对真实数据验证。
- **不覆盖功耗与能效**。指南 3.2.4.4 里的功耗类指标本项目未测，不在 skill 范围内。
