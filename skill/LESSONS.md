## 总览

| 编号 | 技能 | 适用范围 | 使用方法 | 失效条件 | 已验证的复用结果 |

## S1 用 ILA 抓"信号到底有没有到"

**适用**：现象是"完全没反应"，但网络/串口/供电看起来都正常。

**做法**（Vivado 工程模式，不改 RTL）：

1. 写一个 `insert_ila.tcl`，在 `STEPS.OPT_DESIGN.TCL.PRE` 阶段插入调试核：

```tcl
set_property STEPS.OPT_DESIGN.TCL.PRE {D:/path/insert_ila.tcl} [get_runs impl_1]
```

2. 脚本内容要点（**三个容易踩的地方**）：

```tcl
create_debug_core u_ila_0 ila
set_property C_DATA_DEPTH 4096 [get_debug_cores u_ila_0]
# 不要 create_debug_port u_ila_0 clk / probe —— 核心自带 1 个 clk + 1 个 probe！
# 再 create 会报 "exceeds the maximum '1' allowed debug ports"
connect_debug_port u_ila_0/clk [get_nets <时钟网>]
set_property port_width 32 [get_debug_ports u_ila_0/probe0]
connect_debug_port u_ila_0/probe0 $plist
```

3. **网名在综合后会变**。先 `open_run synth_1`，再用
   `get_nets -hier -filter {NAME =~ *关键字*}` 查真实名字，别按 RTL 里的变量名硬写。
   本例中 `eth_rx_clk` 在网表里叫 `u_decision/eth_txc`，用
   `get_clocks -of [get_nets 该网]` 才确认它承载的是 `eth_rxc`。
4. 探针要在编程后设 `PROBES.FILE`（`impl_1/top.ltx`）才会枚举：

```tcl
set_property PROBES.FILE {D:/.../impl_1/top.ltx} [current_hw_device]
refresh_hw_device -update_hw_probes true [current_hw_device]
```

5. 抓完 `upload_hw_ila_data` + `write_hw_ila_data -csv_file`，用 Python 解 CSV 里那几位。

**收益**：一次抓包定位了"4 字节全收到、状态却永不更新"的状态机 bug——靠现象和打印永远查不出来。

## S2 `.bat` 文件的铁律：纯 ASCII + CRLF

**症状**：双击 bat 后出现一堆

```
'frame' 不是内部或外部命令
'irectML' 不是内部或外部命令
```

然后 `exit code = 9009`。

**原因**：cmd.exe 在中文代码页下解析**含多字节字符**的批处理会失步——它按字节偏移读文件，遇到 UTF-8 汉字就把后面的 ASCII 字符吞进一个"双字节字符"里，于是注释碎片被当命令执行，真正的命令行被吃掉。

**判据**：一直能用的那个 bat 是 `CRLF + 0 个非 ASCII`；坏的是 `LF + 若干非 ASCII`。

**规则**：
- 中文只放在 Python 输出里（配 `chcp 65001`），**绝不放进 bat 注释**；
- 文件必须是 CRLF；
- 写完用一行 Python 自检：`sum(1 for b in data if b>127) == 0`。

## S3 "完全没反应"的判据树

同一个现象可能有**四种完全不同**的原因，按顺序查，每步都有硬判据：

| 顺序 | 检查 | 判据 | 若不符说明 |
|---|---|---|---|
| 1 | 设备是否在位流状态 | ARP 表里有目标 MAC | 没烧 / 没上电 / 位流丢了 |
| 2 | 数据源是否在发 | 抓包/探针能收到 | 源没启动，或触发条件没满足 |
| 3 | 数据格式是否正确 | 帧长、字节序、字段范围 | 配置错（如传感器掉回默认模式） |
| 4 | 下游逻辑是否响应 | 用"不依赖上游"的方式单测 | 逻辑 bug |
| 5 | 执行器是否动作 | 直接驱动 IO | 硬件/供电/共地 |

本例的弯路：先怀疑网线、再怀疑端口过滤、最后才发现是**状态机少一个字节**；
而"电机蜂鸣器全死但网络正常"的真正原因是**执行链路挂了 PS 的 FCLK，只烧 PL 时它不跑**。

## S4 执行链路不要依赖"另一个处理器的时钟"

**适用**：Zynq / SoC 上，PL 逻辑用了 PS 提供的 `FCLK_CLK0`。

**坑**：只烧 PL 位流（不 boot Linux、不跑 FSBL）时，PS 未初始化，`FCLK_CLK0` 不输出，
`peripheral_aresetn` 也可能保持低。于是**依赖它的整块逻辑静默冻结**——不报错、不告警，
表现就是"外设完全没反应"，而同一颗芯片上跑在独立晶振上的以太网一切正常，极易误判。

**规则**：凡是"必须一直活着"的链路（安全兜底、执行器驱动），时钟一律取 PL 自己的晶振；
PS 时钟只用于"PS 活着才有意义"的功能。同时记得把 CDC 的 `set_false_path` 改到新时钟上。

## S5 端口冲突：先查再改

**症状**：`bind()` 报 `WinError 10048` / `10013`，程序起不来。

**做法**：
```powershell
netstat -ano | findstr :5001     # 看谁占着
Get-Process -Id <PID>            # 看是什么程序
```
本例 5001 被 **NI 的 `nidmsrv`** 占着（装过 LabVIEW/NI-DAQ 就会常驻）。
默认端口改成 15001，并在绑定处 catch 出友好提示——**比让队友猜"为什么绑不上"强得多**。

另注：`netsh int ipv4 show excludedportrange` 能看到 Hyper-V 保留段，也常是这类报错的来源。

## S6 打包脚本在受限环境里会"假成功"

**症状**：打包脚本打印了 DONE，但产物 zip 还是上一次的。

**原因**：某些受限会话对 `Remove-Item -Recurse` 有批量删除保护，抛异常中断脚本；
而 `Remove-Item <旧zip>` 同样被拦。脚本"看起来跑完了"其实没写新包。

**做法**：
- 清理临时目录用 `try/catch` 包起来，**不能影响已经生成的产物**；
- 删旧产物绕过 PowerShell（例如用 Python `os.remove`）；
- 打完**必须校验**：读 zip 里关键文件的大小与 md5，与源文件对比。

## S7 训练数据自动清洗：用"动不动"区分人和物

**场景**：用 COCO 权重预标注自定义数据集，会把挂着的衣服、海报上的人标成 person。

**做法**：对同一机位的连续帧做**时间中值背景差**，算目标框内的差分能量：
真人在动 → 能量高；静止挂物 → 能量接近 0。实测分布是双峰的
（误检 4~13，真人 49~68，中间无过渡），取中间阈值即可干净分开。

**收益**：无需人工逐张筛，几万帧里挑出"真在动的人"，直接提升 person 类纯度。

## S8 让"不可见"变可见：给调试留 HUD 和开关

一条经验：**任何"状态机 + 传感器"的系统，都要能在画面上直接看到中间量**。

本例加了两行黄字：

```
p0 alpha= +11.2 -> theta= 348.8  radar= 1.30m mono= 1.85m [lidar]
```

- `alpha`：相机算出的方位角；`theta`：映射到雷达坐标系后的角；
- `[lidar]` / `[mono]`：当前距离来自哪一路。

判断"角度对不对上"从"猜"变成"看"。同时留 `CART_DUMP=1` 这样的环境变量开关，
能一键把内部帧导出成 PNG——区分"数据坏了"和"显示坏了"。

## S9 帧率显示要可信

**症状**：控制台显示 58 fps，但实际每秒只更新 5 张图。

**原因**：主循环不等新帧，反复对同一张图推理。此时
`fps = 1/推理耗时` 算出来的是"循环速度"，不是帧率；"看到人"计数也会虚高数倍。

**做法**：
- 用**帧号**做门控：`if frame_cnt == last_processed: 跳过推理`；
- fps 用**帧间隔**统计（`1/(t_now - t_prev_frame)`），推理耗时才单独打印；
- 两个数分开显示（`5.6fps(真) 推理16.5ms`），一眼能看出瓶颈在哪。
