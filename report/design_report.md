> 数据口径：本文所有实测数字均取自 `metrics/metrics.csv`（编号 Mxx 对应）。
> 如需复核，直接查该表最后一列的原始文件。

## 1 选题背景与创新点

### 1.1 要解决的实际问题

低速无人小车（< 10 km/h）在园区、走廊、展台这类人车混行场景里，最刚需的一条不是"导航到哪"，而是**"前方有人就停，别撞"**。这条需求的技术难点不在识别本身，而在于**"感知失效时车必须还能停下来"**。

我们观察到两类常见做法各有硬伤：

| 常见做法 | 问题 |
|---|---|
| 纯 PC / 树莓派跑检测，再发 PWM 给驱动板 | PC 进程崩溃、USB 掉线、系统卡顿任一发生，车就失控往前冲 |
| 纯 MCU（STM32 + 超声/红外） | 算力不够做视觉，只能测距，分不清"人"和"墙" |
| Zynq 上跑 DPU / PYNQ 软核 | 部署链重、迭代慢；很多课程方案最终退化成"PS 跑 Linux + Python" |

### 1.2 本项目的做法与本前人的差异

把链路切成"**感知在前端，决策在后端，兜底在硬件**"三段：

```
OV5640 ──PL 采集──> UDP 图传 ──> PC：YOLO 检测 + 单目测距
                                      │  4 字节距离帧（最近的人多远）
                                      v
                              PL：四态硬件状态机 ──> PWM / 蜂鸣器
```

**创新点一：协议只传"距离"，不传"决策"。**
PC 只回答"最近的人有多远"这一个数（4 字节），该走该停该鸣的策略**焊死在 PL 的状态机里**。这样上层任何东西换掉（模型、语言、操作系统），车的行为不变；而策略一旦放进 PC，就永远无法保证"PC 不在时车是安全的"。

**创新点二：断流即安全，兜底在 400 ms。**
PL 里 400 ms 收不到新帧就进 `SAFE`（停车 + 静音），这个兜底不依赖任何软件存活。它是"感知链路失效"和"车停下来"之间唯一可靠的因果。

**创新点三：决策链路的时钟不依赖 PS。**
早期版本执行链路挂在 PS 的 `FCLK_CLK0` 上，结果**只烧 PL 位流时 FCLK 不跑，电机蜂鸣器全死而以太网照常工作**，现象和"决策没生效"一模一样。改成 PL 自己的 50 MHz 时钟后，只烧位流就能跑，断电重来也不用 boot Linux。

**创新点四：把"看不见的内部状态"变成可观测的。**
用一个 ILA 抓 UDP 收帧通路（原始字节 + 用户侧脉冲 + 状态机 + 输出），直接抓到"`AA 55 01 F4` 四个字节全收到了、`dist_mm` 却一直停在 `0xFFFF`"，从而定位到帧解析状态机多一个状态。这类问题靠打印和猜是查不出来的。

## 2 系统架构与软硬件划分依据

### 2.1 总体架构

```
        ┌─────────────── PC（Windows） ───────────────┐
        │  YOLO11n(19 类) → 只取 person → 单目地面测距  │
        │  5.6 fps / 16.5 ms 每帧（DirectML, 780M）    │
        └───────────────┬─────────────────────────────┘
             UDP 1234   │   ▲                      UDP 5000
          （614408 B/帧）│   │              （4 B 距离帧，20 Hz）
             ▼          │   │                      ▼
   ┌─────────────────────┴───────────────────────────────┐
   │ Zynq-7020                                            │
   │  PL: OV5640 DVP → 异步 FIFO → UDP 分片 → RGMII        │
   │      UDP 收帧 → 四态决策机(400 ms WDT) → PWM/蜂鸣器   │
   │  PS: 未使用（不 boot，仅随时间接地）                  │
   └──────────────────────────────────────────────────────┘
```

### 2.2 为什么这样划分（不是"能跑通"而是"只能这样"）

**① 网口在 PL 侧，这是硬约束。**
RGMII 的 `eth_rxc/eth_rxd/eth_txc/eth_txd` 全部接在 PL 引脚上。PS 侧没有可用网口，所以 PC 的 UDP 报文**只能先进 PL**。同时 Vitis 2025.2 的 PS 侧没有 lwIP 库（`find` 两次为空），"PS 收 UDP → PS 决策"这条路在工具链层面就是断的。这决定了：要么 PL 自己处理网络，要么整个方案推倒重来。

**② 决策放 PL，是因为它要能在"上层全挂"时仍然正确。**
把决策写成 Verilog 状态机，代价是改策略要重编位流（不灵活），换来的是：
- 响应确定：判定到输出是同一个 125 MHz 时钟域内的几个周期；
- 失效安全：没有进程、没有调度、没有 GC，只有 400 ms 看门狗；
- 断电可恢复：只要位流在，行为就在。

**③ 检测放 PC，是因为 PL 没有可用的加速器。**
这台 7020 没有 DPU，纯逻辑跑 CNN 不现实。而 PC 侧 Ryzen AI 1.6.0 + DirectML 在 780M 上能做到 16.5 ms/帧（M12），完全够这个场景。

**④ 为什么不把决策放 PS（Linux）。**
可以让 Linux 读雷达、读 AXI 里的视觉距离、融合后再写回 AXI 控制电机。但那样：Linux 要 boot（几十秒）、要维护、崩了车就失控；而它带来的唯一好处是"改策略不用重编位流"。对一个要跑演示的小车，这个交换不划算。所以本方案里 PS 完全不参与运行。

## 3 AI PC 端

### 3.1 模型与部署选择

- **模型**：YOLO11n，19 类（0~17 为常见物品作干扰项，18 为 `person`），输入 640×640，训练 40 轮。
- **指标**：mAP50 **0.8812**、mAP50-95 0.7435、P 0.8594、R 0.8150（M02~M05）；person 类 mAP50 0.857（M06）。
- **部署**：ONNX + `onnxruntime-directml`，**显式指定 `device_id=0`**（Radeon 780M）。这一步是必须的：DirectML 不指定时会默认选到独显 RTX 4060，导致"以为在核显上跑"的误判。

### 3.2 端侧运行带来的具体收益

- **16.5 ms/帧**（M12），单帧闭环不需要上传云端；
- 图传 5.6 fps 时，PC 侧推理余量充足（16.5 ms vs 178 ms 帧间隔），瓶颈不在算力；
- 全离线：比赛/演示场地常常没有可用外网，云端 API 方案直接不可用。

### 3.3 被放弃的候选方案及原因

| 候选 | 放弃原因 |
|---|---|
| **AMD NPU（Ryzen AI 1.6.0）** | YOLO11n 的 ONNX 含 `Split`/`strided_slice` 等算子，NPU 不支持会大量回退 CPU，实测收益不如 DirectML；且需要 `provider_options['target']`/`xclbin` 等额外配置，踩坑成本高 |
| **纯 CPU 推理** | 同模型 CPU 上单帧耗时远大于 16.5 ms，跟不上 20 Hz 的距离帧下发 |
| **云端 API** | 场地无外网；延迟不可控（几百 ms 抖动），且断网即失效 |
| **传统视觉（背景差分/运动检测）** | 对**静止的人**完全失效，而"人站着不动"恰恰是最需要停的场景。（注：该方法仍被保留用于数据集清洗——`tools/motion_verify.py` 用时间中值背景差区分"真人在动"与"挂着的衣服"） |
| **YOLOv8 替代** | 曾因 NPU 算子兼容性考虑过；最终部署走 GPU/DirectML，11n 的精度/速度比更优，未采用 |

### 3.4 测距与工程细节

- **单目地面假设**：`d = fx·H / (v − v0)`，`H` 为镜头离地高度，`fx` 由水平视场角算出（640 宽 / 60° → 554.3 px）。
- **拒信机制**：人的底边贴图像下沿（脚出画）、或被桌子挡住下缘时，地面公式会给 10 m 这种离谱值。此时**不发距离**（发 `0xFFFF`），让它退化成"看到人但测不出距离"，而不是给一个虚假的"很远"。
- **帧率门控**：主循环只在**收到新帧**时推理。早期不门控时循环跑到 58 fps，实际是在反复算同一张图，`fps` 是假的、"看到人"计数也虚高（1086 次对应 274 帧）。门控后 fps 变成真实值（M11），GPU 也不再空转。

## 4 FPGA / Zynq 端

### 4.1 硬件功能

| 模块 | 文件 | 作用 |
|---|---|---|
| 图像采集与图传 | `rtl/ov5640_udp_pc.v` 及子模块 | DVP 采集 → 异步 FIFO（跨 `cam_pclk`）→ UDP 分片（1288 B/包）→ RGMII 发出，整帧 614408 B（M10） |
| 距离帧接收 | `rtl/motor_decision.v`（eth_rxc 域） | 解析 `AA 55 + u16`，400 ms 看门狗 |
| 四态决策 | 同上 | CLEAR / WARN / STOP / SAFE（阈值 1 m / 3 m，M16/M17） |
| 跨时钟域 | `rtl/top.v` | eth_rxc(125 MHz) → sys_clk(50 MHz)，两级同步器 + `set_false_path` |
| 双电机 PWM | `rtl/motor/motor_diff_ctrl.v` | 20 kHz，占空比 0~100 |
| 蜂鸣器 | `rtl/top.v` | 有源蜂鸣器，电平直出 |

### 4.2 实现方法与两个关键教训

**教训一：帧解析状态机的状态数必须等于字节数。**
帧是 4 字节，状态机却写了 5 个状态（IDLE/HDR1/HDR2/DHI/DLO），`dist_mm` 要到"第 5 个字节"才提交。而包早就结束了，`if (udp_rec_pkt_done) rx_state <= S_IDLE` 直接把它打回 IDLE——**距离永远提交不了**，`dist_valid` 永远不置位，车永远停在 SAFE。
这个 bug 仅靠现象（"完全没反应"）无法定位，最终是 ILA 抓到的：

```
sample 256: en=1 data=AA   ← 帧头
sample 257: en=1 data=55   ← 帧头
sample 258: en=1 data=01   ← 距离高字节
sample 259: en=1 data=F4   ← 距离低字节
dist_mm 全程 = 0xFFFF      ← 从来没更新过
```

**教训二：执行链路不能依赖 PS 的时钟。**
`motor_diff_ctrl` 与跨时钟域同步原本用 `FCLK_CLK0` / `peripheral_aresetn`。只烧 PL 位流时 PS 没有被初始化，FCLK 不跑，于是**电机和蜂鸣器整条链路冻死**，而 PL 的以太网（ARP/UDP）照常工作。现已全部改到 PL 自己的 `sys_clk`（50 MHz，板载 U18 晶振），并且把 CDC 约束从 `clk_fpga_0` 改为 `sys_clk`。

### 4.3 为什么不能由转接板或纯软件替代

**① 不能用"USB-串口转接板 + 单片机"替代 PL。**
- 网口物理上接在 PL 引脚，转接意味着数据要先出 PL 再进转接板，多一层协议转换，延迟与故障点同时增加；
- 转接板上仍是软件（跑在 MCU 上），"断流兜底"又变回软件责任，等于把已经解决的问题重新引入；
- 图传本身（640×480×2 B @ 5.6 fps ≈ 7 MB/s）也必须有硬件通路，转接板扛不住。

**② 不能用"PC 直接发 PWM"替代 PL 决策。**
- PC 上任何进程挂掉/被切走，PWM 就停在最后一个值，车会一直往前开；PL 方案里 400 ms 收不到帧就自动停车静音；
- USB/串口链路抖动（几 ms~几十 ms）叠加在控制环上，无法给出确定的响应时间；
- 决策一旦进 PC，就无法回答"PC 不在时这辆车是否安全"这个问题——而这正是本方案要保证的。

### 4.4 资源与代价

| 指标 | 数值 | 占比 |
|---|---|---|
| Slice LUT | 1702 | 3.20 %（M19） |
| Slice Register | 1943 | 1.83 %（M20） |
| Block RAM Tile | 0.5 | 0.36 %（M21） |
| DSP | 0 | 0（M22） |
| Bonded IOB | 37 | 29.60 %（M23） |
| WNS / WHS | +1.365 ns / +0.057 ns | 全部约束满足（M24/M25） |

**决策逻辑本身几乎不占资源**（DSP 为零、BRAM 半个 tile），代价主要在引脚与时序约束上。这也是"决策硬件化"在这个量级上划算的原因。

## 5 两端协同

### 5.1 通信协议

**图传（板 → PC，UDP 1234，M28）**

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 4 | 帧头 `F0 5A A5 0F` |
| 4 | 2 | 宽（大端，640 = `02 80`） |
| 6 | 2 | 高（大端，480 = `01 E0`） |
| 8 | 614400 | RGB565 像素，行优先 |

整帧 614408 B（M10），按 1288 B 分片发送。接收端靠帧头重同步，**丢包只影响当前帧**。

**距离帧（PC → 板，UDP 5000，M29）**

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 2 | `AA 55` |
| 2 | 2 | 距离 mm（大端），`FFFF` = 无人/测不出 |

4 字节、20 Hz（M14）。PL 侧对端口不做过滤，只校验 MAC/IP/协议类型，因此换端口不影响。

### 5.2 数据流与时序

- 图传 5.6 fps（M11）→ 帧间隔约 178 ms（M13）；
- 每收到一帧就推理一次（16.5 ms，M12），并把当时的距离帧发下去；
- 端到端（画面变化 → PL 收到新距离）估算 **约 200 ms**（M26：帧间隔 178 + 推理 16.5 + 发送周期 ≤ 50）。

### 5.3 时间同步方案

**不做全局时钟同步，是刻意设计。**
距离帧是"最新状态"语义而不是"事件流"：每一帧都是覆盖式的全量状态，丢一帧、乱序一帧都不影响正确性，因此不需要序号、时间戳或握手。板端判断新鲜度只用**本地 400 ms 看门狗**（M15），与 PC 时钟无关——这也避免了"两边时钟漂移导致误判"的整类问题。

### 5.4 异常处理策略

| 异常 | 表现 | 处理 |
|---|---|---|
| PC 进程崩溃 / 网线断 | 板端 400 ms 收不到帧 | 进 `SAFE`：停车 + 静音（M27） |
| 图传丢包 | 帧不完整 | 接收端按帧头 `F0 5A A5 0F` 重同步，丢弃残帧 |
| 距离帧丢一帧 | 无 | 20 Hz 覆盖式，下一帧即恢复 |
| 相机掉线 / 配置失败 | 帧长异常（307200 而非 614408） | 用 `probe_frame_size.py` 判据确认；重新配置 PL 触发 I2C |
| 雷达 UDP 端口被占 | 绑定失败 | 默认端口改为 15001（本机 5001 被 NI 服务占用），并在绑定处给出明确提示 |

### 5.5 雷达接入（COIN-D6）

雷达走**独立的旁挂进程**，不改动任何已定稿的代码：

```
D6 ──USB(CH340, 230400 8N1)──> host/radar/d6_stream.py ──UDP 15001 JSON──> PC 融合
```

关键判断：**D6 不是 LD06**。LD06 是 `0x54 0x2C` 47 字节帧，而 D6 是 85 字节 `AA 55` 帧 + 双字节异或校验，包头都不同，所以工程里现成的 LD06 串口驱动对 D6 永远锁不上包。改走 UDP 后，融合侧只认 `{"angles":[…],"ranges":[…]}` 这一层契约，与雷达型号解耦。

角度仍是那条公式 `theta = theta0 + sign · alpha`。桥的输出恒为"0° = 车头、逆时针为正"，因此**本侧 `ang_sign` 恒取 −1**，倒装由桥内部镜像补偿；`theta0` 只在桥的配置里补一次，两侧不能都加（否则加两遍）。

## 7 失败分析

诚实记录仍然做不好的地方及原因：

**① person 检测的四类固定失败**
只露一条腿 / 隔着玻璃门 / 只露一只脚 / 远小目标。根因是**样本量**：训练集中 person 只有 275 图、502 框（占 9.6 %），姿态与遮挡覆盖不足。已验证"加轮数无效"——15 轮→50 轮，person mAP50 只涨 0.004、召回反而降 0.027，实图检出 19/24 对 19/24 完全打平。要提升只能补数据。

**② 单目测距误差大**
实测距离集中在 0.38~0.62 m（相机高按 0.20 m 代入）。该值与真实站位不符时说明 `CAM_HEIGHT` 未标定；公式对 `H` 是线性敏感的，1 cm 误差直接进来。脚出画时只能拒信（退化成 WARN），此时"有人但不知多远"。

**③ 帧率只有 5.6 fps**
瓶颈既不是网络（1 GbE 上 7 MB/s 只占 3 %）也不是推理（16.5 ms）。指向 OV5640 的寄存器表帧率配置。后果是快速横向运动有拖影，可能漏检。

**④ 相机偶发掉回 8 位模式（花屏）**
OV5640 的 I2C 配置在**位流配置完成瞬间**执行一次。若此时传感器尚未就绪（刚上电/刚重配 PL），配置只写进去一部分，传感器停在默认 8 位 YUV 模式，按 RGB565 解码就是满屏彩虹噪点。判据很硬：正常帧长 614408，异常 307200。处理办法是断电重上电后重新配置 PL。

**⑤ 雷达刚接入，角度方向尚未在车上标定**
硬件链路已通：串口 170.4 帧/s、0 坏帧、10.3 圈/s，扫描 JSON 9.2 Hz、720 点，真实扫描能驱动融合（`source=lidar` 1.93 m，M38）。离线自检 5 个用例也全过。
剩下的问题是**现场标定**：`theta0` 与方向需要用纸箱法确认一次（接口文档 §5.3 给了 2 分钟的判据）。
另外雷达桥文档里"倒装应把 `ang_sign` 改成 +1"的说法，与其自身代码（输出恒为逆时针为正）矛盾，本报告以代码为准取 −1——这类"两处联动参数"最容易出左右镜像，必须实测收敛。
此外雷达测的是"最近障碍"而非"最近的人"，空房间里墙也会触发，所以桥的距离帧通路默认关闭，只把扫描喂给视觉融合。

**⑥ 无法 QSPI 固化**
板上有 Winbond W25Q256JVEQ，但用 u-boot 探测 flash 返回 `unrecognized JEDEC id bytes: 90, d8, ff`，x1/x4 两种模式结果相同且 IRQ 轮询超时。判断是 PS7 配置里 QSPI 未使能（`ps7_init` 未配置对应 MIO）。当前只能 JTAG 烧 PL，**断电即丢失**，需重新烧写。

## 8 复现说明

### 8.1 硬件

| 项 | 型号/接法 |
|---|---|
| 主板 | 正点原子 ZYNQ7020（xc7z020clg400-2） |
| 相机 | OV5640（DVP 并口，FPC 排线） |
| 底盘 | 双轮差速 + L298N，ENA/IN1/IN2/ENB/IN3/IN4 接 PL |
| 蜂鸣器 | 板载有源蜂鸣器（M14，高电平响） |
| 网线 | PC ↔ 板载网口（**接 PL 侧**），PC 固定 192.168.1.102，板子 192.168.1.10 |
| 供电 | 电机与逻辑分开供电，共地 |

### 8.2 环境

- PC：Windows 11，Python 3.12，`pip install -r host/deploy/requirements.txt`（onnxruntime-directml、opencv-python、numpy）
- FPGA：Vivado / Vitis 2025.2

### 8.3 步骤

**第 1 步 配置 PL（每次上电都要做，因为现在只能 JTAG 烧）**
Vivado → Hardware Manager → 连接 → `Program Device` → 选 `fpga/build/top.bit`。
> 烧完 PL 会同时完成一次 OV5640 的 I2C 配置。**若相机是后插的，或画面花屏，断电重上电再烧一次。**

**第 2 步 验证图传（不开窗口）**
```bash
python metrics/scripts/probe_link.py            # 4 s 内应收到几百个包
python metrics/scripts/probe_frame_size.py      # 帧长必须是 614408；307200 = 相机在 8 位模式
```

**第 3 步 验证决策链（不接相机也能测）**
```bash
python metrics/scripts/test_cmd_frame.py --hold 3
```
应依次出现：70 % 前进（静音）→ 前进 + 间歇嘀 → 停车 + 连续响 → 停发后 0.8 s 静音。

**第 4 步 跑完整链路**
```bash
host/deploy/run_fusion.bat
```
或手动：
```bash
cd host/app
set CART_MODEL=..\model\best.onnx
python detect_fusion_live.py --lidar none --cmd-udp 192.168.1.10:5000 --send
```
画面上会显示 `状态 / 距离 / 蜂鸣`，人靠近时应依次变 WARN → STOP。

**第 5 步 重建工程（改 RTL 时）**
```bash
vivado -mode batch -source fpga/src/tcl/01_project.tcl
vivado -mode batch -source fpga/src/tcl/02_build.tcl
```
工程建在 `fpga/src/prj/`，位流产物是 `fpga/src/prj/7020.runs/impl_1/top.bit`，
需要交付时手动覆盖到 `fpga/build/top.bit`。

### 8.4 结果比对

跑完第 4 步后，对照 `metrics/metrics.csv`：
- 帧率应接近 5.6 fps（M11）；
- 单帧推理约 16 ms（M12）；
- 人进入 1 m 内应停车 + 连续响（M16/M18）；
- 拔掉网线，0.4 s 内应停车并静音（M15/M27）。

任一项明显不符，先查 `docs/hardware_setup.md` 的排查顺序。
