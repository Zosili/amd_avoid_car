## 3 怎么读（重要）

**① 那个 50.59% 的"未命中"不是故障。**

`latency_stats` 的未命中率 = 间隔超过 `period × 1.1` 的比例，它假设环有**固定标称周期**。
而本项目的融合环是**帧驱动**的：有图才推理，没图就等。所以它的"周期"等于帧间隔，
中位 257 ms（≈3.9 fps）——我用 `--period 200` 只是随手给个参照值，
按定义就会有一半样本在 200 ms 以上。

**对帧驱动的环，正确的用法是 `--period 0`（只报分位数、不判定）**，
或者按实测中位值给 `--period 257` 再看波动。这也是这个工具"失效条件"里该写清楚的一条。

**② 真正有价值的结论：瓶颈不在 AI。**

```
推理 16.5 ms  ÷  帧间隔 257 ms  ≈  6%
```

推理只占一帧预算的 **6%**，剩下 94% 花在等图（OV5640 采集 + PL 打包 + UDP 传输 + PC 收包解码）。
所以：

- 换更小的模型、开 FP16、上 NPU —— 对**提帧率几乎无效**，因为省下的那几毫秒淹没在 240 ms 的等待里；
- 想提帧率只能动图传链路（这是本项目 5 fps 上限的真实来源）；
- 但换更快的推理对**降延迟**仍有一点意义（单帧端到端少 10 ms 左右）。

这两件事很容易在报告里被写成"推理太慢所以帧率低"——**数据不支持这个说法**。
