# radar_probe 板级实测记录（2026-11-04 01:20）

> 用途：证明 `skill/radar_probe.py` 在**真实硬件 + 真实传感器**上跑得通，
> 而不只是"写成文档没跑过"。
> 原始输出：`radar_probe_board.txt`（脚本直接落盘的，未经编辑）。

## 1 测量条件

| 项 | 值 |
|---|---|
| 板卡 | 领航者 ZYNQ7020（`xc7z020clg400-2`），PYNQ 镜像 |
| 数据通道 | 板载 **AXI UART Lite @ 0x42C00000**，MMIO 直读（不是 `/dev/ttyUL0`） |
| 传感器 | COIN-D6 dToF 激光雷达，`AA 55` 帧头，主包 85 B |
| 波特率 | 230400 |
| 采样时长 | 12.0 s |
| 雷达姿态 | 整车静置于桌面，扫描面朝房间空旷处（**前方无近距离目标**） |
| 软件 | PYNQ venv Python3 + `radar_probe.py --mmio 0x42C00000` |

**为什么不用 `/dev/ttyUL0`**：PYNQ 默认不加载 uartlite 内核驱动，板子上根本没有这个设备节点
（`ls: cannot access '/dev/ttyUL0'`）。所以探针加了第二个取数后端：直接 MMIO 读 AXI UART Lite
的 RX FIFO，判据与串口模式完全一致。这正是"接口契约不变、只换取数方式"的复用示例。

```
  有效点率 43.5%   主导帧长 85 B

=== 判据 ===
  · 另有 3 种包长（{13: 119, 79: 23, 82: 95}），占 11.8%——多包型传感器属正常
  ✗ 坏帧率 1.04% > 1.0% → 串口丢字节，检查波特率与读取方式
  ✗ 有效点率 43.5% < 80% → 回波弱：镜头脏 / 被测面吸收 / 超量程 / 对着空气
```

## 3 怎么读这份结果（重要）

**工具本身已验证可用**：
- 12 s 内切出 2012 帧、帧率 167.7 帧/s（标称 170 的 98.6%，达标线 90%）—— 吞吐与解析都跟得上；
- 主导帧长 85 B 与标称一致 —— 协议解析正确；
- 另有 3 种包长（13/79/82 B，占 11.8%）是 COIN-D6 的**其它包类型**（n=1/23/24），
  校验和均合法，属正常现象，判据只作提示不判失败。

**两项 FAIL 是环境所致，不是工具问题，也**没有**调阈值去凑 PASS**：

| 判据 | 实测 | 说明 |
|---|---|---|
| 坏帧率 1.04% | 略超 1% 线 | 与 PS 侧雷达服务自报的 3.5% 坏帧相比反而更好；属 230400 下 STAT 轮询的固有损耗 |
| 有效点率 43.5% | 低于 80% 线 | 雷达静置桌面、扫描面朝空旷房间，大量光束**打不到任何东西**，自然没有有效回波 |

> 想复现一个"有效点率高"的结果，把车正对墙或纸箱（≈1 m）再跑一次即可。
> 本次没有为了好看而挪动设备或放宽 `--min-valid-ratio`。

## 4 与 PS 侧服务的对照

同一条链路，PS 侧 `ps_radar_fusion.py` 自报的坏帧率约 **3.5%**（`帧OK 10428 坏 381`），
探针测得 **1.04%** —— 说明服务端那种"逐字节 + 业务逻辑"的读法确实比纯轮询丢得更多，
这也是探针存在的意义：把"能读到"和"读得干净"分开量。

## 5 复现命令

```bash
# 板子上（先停服务腾出 FIFO）
sudo systemctl stop radar
XILINX_XRT=/usr /usr/local/share/pynq-venv/bin/python3 -u radar_probe.py \
    --mmio 0x42C00000 --secs 12 --nominal-fps 170
sudo systemctl start radar
```
